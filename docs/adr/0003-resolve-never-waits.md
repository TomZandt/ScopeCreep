# Resolve never waits for scopecreep

Turning the Sender on must not change Resolve's playback frame rate. This constraint is invisible in the code but shapes all of it. The Sender's render call starts a copy and returns at once; it never blocks on the app, a lock or a full buffer. If the app falls behind, it drops Scope frames and shows that it did; it never slows Resolve. When no app is listening, the Sender does no work at all. Every change to the Sender or the transport is benchmarked with the Sender on and off at the project's resolution and frame rate.

Stage 0 proved this is achievable at UHD 32-bit float, 23.976 to 60 fps, on an RTX 3070 Ti, with no change to Resolve's playback rate and no dropped frames, provided the Sender uses Resolve's CUDA render path and an asynchronous pinned-memory copy (`docs/stage0-report.md`, ticket #12). On the CPU path Resolve copies frames to host memory itself and UHD playback at 50 and 60 fps slows to about 30 fps, so the CUDA path is required. Graphics memory is the tightest resource: keep the Sender's staging buffers small. Headroom is real but finite: an uncapped render lost about 14 to 18% throughput with the copy on.
