# Resolve never waits for scopecreep

Turning the Sender on must not change Resolve's playback frame rate. This constraint is invisible in the code but shapes all of it. The Sender's render call starts a copy and returns at once; it never blocks on the app, a lock or a full buffer, and it never allocates graphics memory, pins host memory or touches the file system. That work runs on the Sender's own worker thread; a frame that arrives while the worker is building a new ring passes through and is counted as dropped ("Sender busy"). If the app falls behind, it drops Scope frames and shows that it did; it never slows Resolve. When no app is listening, the Sender does no work at all. Every change to the Sender or the transport, and every release, is checked with the Sender off, on, and on with the app at UHD 50 fps, the heaviest case the product owner works in (PAL), using `harness/experiments/uhd50_bench` (#20). Higher frame rates are out of scope until they become a goal (#31).

Stage 0 proved this is achievable at UHD 32-bit float, 23.976 to 60 fps, on an RTX 3070 Ti, with no change to Resolve's playback rate and no dropped frames, provided the Sender uses Resolve's CUDA render path and an asynchronous pinned-memory copy (`docs/stage0-report.md`, ticket #12). On the CPU path Resolve copies frames to host memory itself and UHD playback at 50 and 60 fps slows to about 30 fps, so the CUDA path is required. Graphics memory is the tightest resource: keep the Sender's staging buffers small. Headroom is real but finite: an uncapped render lost about 14 to 18% throughput with the copy on.

The first release check (2026-11-16, #20, `docs/findings/20-performance-benchmark.md`) passed: at UHD 50 Resolve played at 50 fps in all three cases, and the app missed no frames.
